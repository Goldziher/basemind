title: Shared memory
description: >
  Per-repo memory agents can write to and search. The worktrees of one checkout share it;
  other clones and unrelated repos do not.
---

basemind provides a shared memory layer scoped to your repository: agents can store notes and search
them by meaning.

## How it works

Each repository on a machine has its own memory store, keyed by the path of its main worktree. The
linked worktrees of that checkout share the store; another clone, even of the same remote, has its
own. When you work on an unrelated project, that memory stays separate — no leakage.

Any agent can:

- **Write a note:** `memory_save {"key":"auth-flow","value":"…"}` stores a key-value pair.
- **Search by meaning:** `memory_search {"query":"password validation"}` finds stored notes by
  semantic similarity, even if the exact words don't match.
- **Retrieve exact keys:** `memory_search {"key":"auth-flow"}` fetches one stored note.
- **List by prefix:** `memory_search {"prefix":"auth-"}` finds all keys starting with a prefix.
- **Delete:** `basemind memory delete auth-flow` removes a note, and `basemind memory clear` removes
  every note of the repository. Deleting is CLI only; no MCP tool removes a note.

## What notes look like

Notes are simple key-value pairs:

```text
key: "sqlinjection-mitigation"
value: "All user inputs are parameterized at the data layer via the Query class.
        Prepared statements escape at the database driver level."
```

The key is a short identifier; the value is prose explaining what you want to remember.

## Uses

Shared memory is useful for:

- **Architectural decisions:** "These modules are always deployed together."
- **Refactoring markers:** "This legacy API is being phased out in favor of V2."
- **Gotchas and workarounds:** "On Windows, the build requires Visual Studio 2022+."
- **Patterns:** "Auth tokens are stored in Redis with a 1-hour TTL."
- **Cross-session context:** "The last agent was working on the payment module."

## Semantic search

Memory search is powered by LanceDB's vector embeddings. You don't need exact keywords — search
by meaning. If you stored "All inputs are parameterized at the database driver", you can find it
with `memory_search {"query":"SQL injection prevention"}`.

## Scoping

The store is `cache/repos/<key>/memory.fjall` under the data home, where `<key>` hashes the
canonical path of the repository's main worktree. Inside the store, notes are filed under the
normalised `origin` URL, or `path:<worktree>` when there is no `origin`. So:

- The worktrees (`git worktree add`) of a repository with an `origin` share notes.
- A second clone at another path has its own store and sees none of the first clone's notes, even
  with the same `origin`.
- Moving a repository, or cloning it again at another path, starts with no notes; the old ones
  stay under the old path's key.
- Adding or changing `origin` (`git remote set-url`) hides the existing notes; they stay in the
  store under the old scope.
- A repository without `origin` files notes per worktree, so its worktrees do not share them.
- Nothing is synced between machines.

This scoping is automatic — you don't configure it.
